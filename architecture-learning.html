從零學三大架構

這份是給「看了一堆教學還是搞不清楚」的人寫的。我們會從一個真實場景開始，看同一個功能在三種架構下怎麼寫、bug 怎麼發生、測試怎麼寫。

前言：你會學到什麼

很多教學會直接丟一堆名詞 — Aggregate、Bounded Context、Use Case。我懂為什麼你會卡。這次我們反過來：

  1. 先用 5 分鐘把基本詞彙講清楚（層、依賴、介面、Mock）。
  2. 設定一個你完全能想像的場景：銀行轉帳。
  3. 用同一個場景寫三遍：N-Tier → Clean Architecture → DDD。
  4. 每一遍都演示同一個 bug 怎麼發生（或不發生）、同一個測試怎麼寫。
  5. 最後回答你的疑問：「層之間還是會互相呼叫，那差別到底在哪？」

看完這份，你不會變成架構大師，但你會看出三種架構的關鍵差異 — 而且能講給別人聽。

第 1 章：基本詞彙先講清楚

後面要用到的字都先解釋一次。這章很短，但跳過你會卡。

1.1 什麼叫「層」（Layer / Tier）？

「層」就是把程式碼按職責分組。每個檔案放在一個資料夾裡，這個資料夾代表一個層。

用餐廳比喻

餐廳有四種人：服務生、廚師、採購、農夫。客人不會直接跟農夫點菜，農夫也不會跑到桌邊上菜。每個角色職責清楚 — 這就是「分層」。

餐廳角色對應軟體層職責
服務生Web / UI 層跟客人互動、收訂單
廚師Business / Application 層實際做菜（業務邏輯）
採購Repository 層把食材送到廚房
農夫Database真正生產食材

1.2 什麼叫「依賴」（Dependency）？

A 依賴 B：A 的程式碼裡用到 B、需要 B 才能跑。

範例：A 依賴 B
public class A
{
    private B _b = new B();   // ← A 的程式碼裡寫了 B，所以 A 依賴 B

    public void DoSomething()
    {
        _b.HelpMe();           // ← 沒有 B，A 跑不起來
    }
}

「依賴方向」是指：誰知道誰存在。上面這段：A 知道 B 存在，但 B 完全不知道 A 存在。所以箭頭是「A → B」。

為什麼依賴方向重要？

如果 A 依賴 B，那改 B 可能會影響 A，但改 A 不會影響 B。所以「讓核心業務不依賴技術細節」=「就算 DB 換了、Web 框架換了，核心業務也不用動」。這就是 Clean Architecture 的整個核心觀念。

1.3 什麼叫「介面」（Interface）？

介面是「契約」。它說「我有這些方法」，但不說「怎麼實作」。

介面 vs 實作
// 介面：只規定「有什麼方法」
public interface IAccountRepository
{
    Account Get(int id);
    void Save(Account account);
}

// 實作 1：用 SQL Server
public class SqlAccountRepository : IAccountRepository
{
    public Account Get(int id) { /* 用 SQL 查 */ }
    public void Save(Account account) { /* 用 SQL 寫 */ }
}

// 實作 2：用 MongoDB
public class MongoAccountRepository : IAccountRepository
{
    public Account Get(int id) { /* 用 Mongo 查 */ }
    public void Save(Account account) { /* 用 Mongo 寫 */ }
}

使用方只寫 IAccountRepository，不寫具體的 SqlAccountRepository。要換實作只要換注入的那行，使用方完全不動。

用插座比喻

「USB 介面」規定形狀和針腳。手機、耳機、隨身碟都實作這個介面。電腦只認 USB 介面，不在乎你插的是哪個牌子的手機 — 這就是「依賴介面，不依賴實作」。

1.4 什麼叫「Mock」（假物件）？

寫測試時，不想真的連 DB（慢、要準備資料、可能爆掉），所以做一個「假的 Repository」假裝是真的。這個假的就叫 Mock。

Mock 範例
// 測試「轉帳餘額不足會失敗」這條規則

// 真實情況：要連 DB、塞兩筆帳戶資料、跑完還要清資料
// Mock 做法：
var fakeRepo = new Mock<IAccountRepository>();
fakeRepo.Setup(r => r.Get(1)).Returns(new Account { Balance = 50 });
fakeRepo.Setup(r => r.Get(2)).Returns(new Account { Balance = 0 });

var service = new TransferService(fakeRepo.Object);
// 試圖從帳戶 1（餘額 50）轉 100 到帳戶 2 → 應該失敗
Assert.Throws<Exception>(() => service.Transfer(1, 2, 100));

「Mock 的麻煩程度」是評估架構好壞的重要指標。越難 Mock，代表程式碼跟外部依賴綁太緊。後面你會看到 DDD 完全不需要 Mock。

第 2 章：場景設定 — 銀行轉帳

場景

需求

要做一個 API：POST /transfer，把錢從 A 帳戶轉到 B 帳戶。聽起來很簡單，但業務規則很多。

業務規則（記住這 5 條，後面整篇都在解這個問題）
  1. 轉出帳戶餘額必須足夠（不能讓帳戶變負數）
  2. 轉出帳戶不能是凍結狀態
  3. 不能轉給自己
  4. 轉帳金額必須大於 0
  5. 單日累計轉出不能超過 100 萬

為什麼挑這個場景？因為它很簡單你能想像，但業務規則違反就會出大事（帳戶變負數＝銀行虧錢）。這種「規則必須被嚴格遵守」的場景，正是要區分三種架構的最佳測試。

關鍵問題

規則 1（餘額必須足夠）寫在哪裡？
— 你回答的位置，就決定了你用的是哪一種架構。

第 3 章：N-Tier 寫法

最常見的寫法。三層：Controller → Service → Repository。規則寫在 Service 裡。

3.1 完整程式碼（每個 class 都標清楚在哪一層）

資料模型Account.cs

📦 純資料容器，沒有任何方法
// ─────────────────────────────────────────────
// 這個 class 只是「資料的形狀」，沒有業務邏輯
// 所有屬性都是 public get; set; — 任何人都能改
// ─────────────────────────────────────────────
public class Account
{
    public int Id { get; set; }
    public decimal Balance { get; set; }       // ← 任何人都能直接改
    public bool IsFrozen { get; set; }         // ← 任何人都能直接改
    public decimal DailyTransferred { get; set; }
}
⚠️ 注意這個現象

這種「只有屬性、沒有方法」的物件叫做「貧血模型」（Anemic Model）。它只是個資料袋。後面會看到這個設計是萬惡之源。

Repository 層AccountRepository.cs

🟢 Repository 層 — 跟 DB 對話
// ─────────────────────────────────────────────
// 職責：把 SQL 包起來，給上層用
// 上層（Service）會呼叫這個
// 這層會呼叫：DB
// ─────────────────────────────────────────────
public class AccountRepository
{
    private readonly string _connStr;

    public Account Get(int id)
    {
        // 連 DB、撈資料、轉成 Account 物件回傳
        using var conn = new SqlConnection(_connStr);
        return conn.QueryFirstOrDefault<Account>(
            "SELECT * FROM Accounts WHERE Id = @Id", new { Id = id });
    }

    public void Save(Account account)
    {
        // 寫回 DB
        using var conn = new SqlConnection(_connStr);
        conn.Execute(
            "UPDATE Accounts SET Balance=@Balance, DailyTransferred=@DailyTransferred WHERE Id=@Id",
            account);
    }
}

Service 層TransferService.cs（重點）

🟧 Service 層 — 業務規則寫在這
// ─────────────────────────────────────────────
// 職責：處理「轉帳」這個業務動作
// 上層（Controller）會呼叫這個
// 這層會呼叫：AccountRepository
// ─────────────────────────────────────────────
public class TransferService
{
    private readonly AccountRepository _repo;  // ← 直接依賴具體類別

    public TransferService(AccountRepository repo)
    {
        _repo = repo;
    }

    public void Transfer(int fromId, int toId, decimal amount)
    {
        // 步驟 1：往下呼叫 Repository 拿資料
        var from = _repo.Get(fromId);
        var to = _repo.Get(toId);

        // 步驟 2：在這裡檢查所有業務規則 ← 重點
        if (from == null || to == null)
            throw new Exception("帳戶不存在");
        if (amount <= 0)
            throw new Exception("金額必須大於 0");
        if (fromId == toId)
            throw new Exception("不能轉給自己");
        if (from.IsFrozen)
            throw new Exception("帳戶已凍結");
        if (from.Balance < amount)
            throw new Exception("餘額不足");
        if (from.DailyTransferred + amount > 1_000_000)
            throw new Exception("超過單日上限");

        // 步驟 3：直接修改 Account 的屬性 ← 注意這裡
        from.Balance -= amount;
        from.DailyTransferred += amount;
        to.Balance += amount;

        // 步驟 4：往下呼叫 Repository 存回去
        _repo.Save(from);
        _repo.Save(to);
    }
}

Controller 層TransferController.cs

🟦 Web 層 — 處理 HTTP 請求
// ─────────────────────────────────────────────
// 職責：接收 HTTP 請求、呼叫 Service、回傳結果
// 上層：客戶端（前端、Postman）
// 這層會呼叫：TransferService
// ─────────────────────────────────────────────
[ApiController]
public class TransferController : ControllerBase
{
    private readonly TransferService _service;  // ← 依賴 Service

    public TransferController(TransferService service)
    {
        _service = service;
    }

    [HttpPost("transfer")]
    public IActionResult Transfer([FromBody] TransferDto dto)
    {
        try
        {
            _service.Transfer(dto.FromId, dto.ToId, dto.Amount);
            return Ok();
        }
        catch (Exception ex)
        {
            return BadRequest(ex.Message);
        }
    }
}

3.2 災難現場：別人寫的 bug

三個月後，另一個工程師「小明」要做新功能：「給 VIP 客戶加值點數」。他完全不知道你之前寫的轉帳規則。他寫了：

🟧 小明寫的新 Service
public class BonusService
{
    private readonly AccountRepository _repo;

    public void AddBonus(int accountId, decimal bonus)
    {
        var account = _repo.Get(accountId);
        account.Balance += bonus;   // ← 直接改 Balance！
        _repo.Save(account);
    }
}

看起來沒問題。但 bonus 是從前端傳來的 decimal，使用者可以傳負數！

🔴 災難發生

使用者送出 { accountId: 123, bonus: -999999 }。
系統乖乖把帳戶餘額減 999999，變負數。銀行虧錢。

為什麼會這樣？因為 Account.Balance 是 public set;，任何地方都能直接改。TransferService 裡寫的「餘額不能小於 0」這條規則，只在 TransferService 內有效。其他 Service 完全可以繞過。

業務規則跟資料分開放，所以規則只能保護「特定的入口」（轉帳），保護不了資料本身。這是 N-Tier 最大的缺陷。

3.3 為什麼這個測試很痛苦

你想寫單元測試驗證「餘額不足會被擋下」。試試看：

N-Tier 測試
[Test]
public void 餘額不足要擋下()
{
    // 1. 建假的 Repository
    var mockRepo = new Mock<AccountRepository>();

    // 2. 設定假的回傳值（這裡卡住：AccountRepository 不是介面，
    //    Mock 不出來，要先去把它改成介面 IAccountRepository）
    mockRepo.Setup(r => r.Get(1))
            .Returns(new Account { Id = 1, Balance = 50 });
    mockRepo.Setup(r => r.Get(2))
            .Returns(new Account { Id = 2, Balance = 0 });

    // 3. 注入 Service
    var service = new TransferService(mockRepo.Object);

    // 4. 真正的測試只有這一行
    Assert.Throws<Exception>(() => service.Transfer(1, 2, 100));
}
⚠️ 痛點清單

1. 要先把 AccountRepository 改成介面才能 Mock
2. 真正想驗的「餘額不足擋下」這條規則，被埋在一坨 Mock 設定後面
3. 每測一條規則都要重設一次 Mock
4. Mock 設錯了測試會偽陽性（明明壞掉但測試過了）

第 4 章：Clean Architecture 寫法

Clean Architecture 解決「依賴方向」的問題，但還沒解決「業務規則放哪」的問題。先看它做了什麼。

4.1 核心觀念：依賴反轉（Dependency Inversion）

術語
Dependency Inversion 依賴反轉

把「直接依賴具體類別」改成「依賴介面」。表面上只是中間多了個介面，實際上把依賴方向「轉了過來」。

之前 vs 之後

❌ N-Tier（直接依賴）

Service 直接 new Repository 或建構子吃 AccountRepository。

public class TransferService
{
    private readonly AccountRepository _repo;
    //                ↑ 具體類別

    public TransferService(AccountRepository repo)
    { _repo = repo; }
}

問題：換 ORM、Mock 測試都要動 Service。

✅ Clean Architecture（依賴介面）

Service 依賴 IAccountRepository 介面，不知道實作是誰。

public class TransferService
{
    private readonly IAccountRepository _repo;
    //                ↑ 介面

    public TransferService(IAccountRepository repo)
    { _repo = repo; }
}

好處：換 ORM、Mock 測試只動實作端，Service 不動。

4.2 程式碼變化（差異不大）

檔案結構分四個專案：

Domain/         ← Account.cs（純粹資料模型，無依賴）
Application/    ← TransferService.cs、IAccountRepository.cs（介面定義在這）
Infrastructure/ ← AccountRepository.cs（實作 IAccountRepository，用 SQL）
Web/            ← TransferController.cs

關鍵：介面定義在 Application 層

🟧 Application/IAccountRepository.cs
// 介面定義在這裡，但實作在 Infrastructure
// ⚠️ 注意：介面跟實作不在同一層！
public interface IAccountRepository
{
    Account Get(int id);
    void Save(Account account);
}
🟢 Infrastructure/SqlAccountRepository.cs
// 實作介面（介面在 Application 層）
public class SqlAccountRepository : IAccountRepository
{
    public Account Get(int id) { /* SQL */ }
    public void Save(Account a) { /* SQL */ }
}
💡 這就是「依賴反轉」的精髓

Application 層需要存取資料，但介面是它自己定義的。Infrastructure 層來實作這個介面。
所以表面上 SqlAccountRepository 在「下面」，但箭頭其實是從下往上指（Infrastructure 依賴 Application）。
這就是依賴方向被「反轉」了。

呼叫關係圖

測試變多簡單？

Clean Architecture 測試
[Test]
public void 餘額不足要擋下()
{
    // 因為 IAccountRepository 是介面，Mock 直接做
    var mockRepo = new Mock<IAccountRepository>();
    mockRepo.Setup(r => r.Get(1)).Returns(new Account { Id = 1, Balance = 50 });
    mockRepo.Setup(r => r.Get(2)).Returns(new Account { Id = 2, Balance = 0 });

    var service = new TransferService(mockRepo.Object);
    Assert.Throws<Exception>(() => service.Transfer(1, 2, 100));
}

跟 N-Tier 比，少了「要先把 Repository 改成介面」這個前置步驟。但本質上 Mock 設定還是一樣多。

4.3 還沒解決的問題

🔴 小明的 bug 還是會發生

因為 Account 還是貧血模型（Balance 還是 public set;）。
BonusService.AddBonus() 一樣可以直接改 Balance 為負數。
本章的範例還沒解決這個問題。

Clean Architecture 提供了「依賴方向反轉」的骨架 — DB、框架可以換、單元測試也好寫。
但「業務規則內聚到 Entity 自己」這個動作，本章還沒示範怎麼做 — 第 5 章 DDD 來補完。
在進入下一章之前，先補兩個 Clean Architecture 容易踩坑的細節。

4.4 介面要放哪一層？

「依賴反轉」最容易誤解的地方就在這。程式碼裡有 interface 不代表就是 Clean Architecture。關鍵在：interface 定義在哪一層。

錯誤寫法：interface 跟實作住在同一層

🟢 Infrastructure/IAccountRepository.cs（interface 在這）
// interface 跟下面的 SqlAccountRepository 一起住在 Infrastructure
public interface IAccountRepository
{
    Account Get(int id);
    void Save(Account account);
}
🟢 Infrastructure/SqlAccountRepository.cs（實作也在這）
public class SqlAccountRepository : IAccountRepository
{
    public Account Get(int id) { /* SQL */ }
    public void Save(Account a) { /* SQL */ }
}
🟧 Application/TransferService.cs
public class TransferService
{
    private readonly IAccountRepository _repo;
    // ↑ 看起來用了 interface 沒錯，但這個 interface 是去 Infrastructure 借的
    // 所以 Application 還是要先「認得」Infrastructure 才能用
    // 依賴箭頭沒變：Application → Infrastructure
}
🔴 這只是「假的依賴反轉」

有 interface ≠ 依賴反轉。如果 interface 跟實作住在同一層，依賴方向沒變，只是中間多了一個轉接器，本質上跟 N-Tier 沒差。

正確寫法：interface 放在「需要它的那一層」

🟧 Application/IAccountRepository.cs（interface 跟使用者住一起）
// 介面定義在 Application — 因為這裡才需要它
public interface IAccountRepository
{
    Account Get(int id);
    void Save(Account account);
}
🟧 Application/TransferService.cs
public class TransferService
{
    private readonly IAccountRepository _repo;
    // ↑ 這個 interface 是 Application 自己定義的
    // 完全不需要看 Infrastructure 一眼
}
🟢 Infrastructure/SqlAccountRepository.cs（實作要去 Application 拿規格）
public class SqlAccountRepository : IAccountRepository
{
    // 這個 class 必須先「認得」Application 的 IAccountRepository 才能實作
    // 所以依賴箭頭：Infrastructure → Application（外圈依賴內圈）
    public Account Get(int id) { /* SQL */ }
    public void Save(Account a) { /* SQL */ }
}
✅ 真的依賴反轉

Application 自己定 interface，Infrastructure 必須「配合」這個 interface 來做事。
依賴箭頭從原本的「上往下」反過來變成「下往上」（外圈依賴內圈）。這就是 Clean Architecture 的核心。

用裝修比喻

假反轉：你跑去水電工的店，拿水電工準備好的合約規格給他簽 — 你還是被水電工綁著。
真反轉：你寫好你家要什麼（規格），水電工照你寫的規格做 — 換哪個水電工都可以，因為規格是你訂的。

4.5 跨層傳資料：用 DTO 不要傳 Entity

看一個常見的寫法：

🟦 Web/AccountController.cs
[HttpGet("{id}")]
public Account Get(int id)
{
    return _service.GetAccount(id);
    // ↑ 直接把 Account 物件丟出去當 API 回應
}

看起來合理對不對？但 Clean Architecture 不建議這樣做。為什麼？

  1. API 規格綁住業務邏輯：你想把 API 欄位從 balance 改成 availableAmount，就得動 Account。但 Account 是業務概念，不該為 API 改。
  2. 意外洩漏內部欄位：Account 內部可能有 DailyTransferred（單日累計）、InternalNote（內部備註），你不見得想讓前端看到。但序列化（轉成 JSON）時會被默默全部讀出來。
  3. API 加版本變難搞：如果未來 v1 跟 v2 API 欄位不一樣，Account 會變成「兩個 API 都要遷就」的怪物。

正確做法：跨層傳資料用 DTO。

術語
DTO Data Transfer Object，資料傳輸物件

一個專門「跨層裝資料」的純資料盒子。沒有業務邏輯，只有屬性。每一層可以有自己的 DTO，互相不干擾。

🟦 Web/Dtos/AccountDto.cs（API 自己的資料盒子）
public class AccountDto
{
    public int Id { get; set; }
    public decimal Balance { get; set; }
    // 注意：DailyTransferred 不放在這 → 前端看不到
    // 想改 API 欄位名就直接改這個 class，不會動到 Account
}
🟦 Web/AccountController.cs（修正版）
[HttpGet("{id}")]
public AccountDto Get(int id)
{
    var account = _service.GetAccount(id);
    // 把 Account（Domain 物件）轉成 AccountDto（API 物件）才回傳
    return new AccountDto
    {
        Id = account.Id,
        Balance = account.Balance
    };
}
用寄包裹比喻

不用 DTO：你把整個房間（Account）打包寄給朋友 — 朋友會收到一堆他根本不需要的東西，連你的內部備註都會看到。
用 DTO：你只把朋友需要的東西（Id、Balance）放進紙箱寄過去 — 乾淨、隱私、互不影響。

會多寫一些「轉換」程式碼（Account → AccountDto），但這是換取「Domain 不被外面污染」的代價。實務上有 AutoMapper、Mapster 這類工具可以自動幫你做轉換。

第 5 章：DDD 寫法

DDD 的核心動作只有一個：把業務規則從 Service 搬進 Account 自己。

5.1 把規則搬進 Account

Domain 層Account.cs（DDD 版）

🟪 Domain 層 — Account 自己保護自己
// ─────────────────────────────────────────────
// 重點變化：
// 1. Balance 改成 private set; → 外部不能直接改
// 2. 加上業務方法 Withdraw / Deposit
// 3. 規則寫在方法裡 → 任何想動 Balance 的人都繞不過
// ─────────────────────────────────────────────
public class Account
{
    public int Id { get; private set; }
    public decimal Balance { get; private set; }      // ← 只能讀，不能從外部改
    public bool IsFrozen { get; private set; }
    public decimal DailyTransferred { get; private set; }

    // ===== 業務方法 1：扣款 =====
    public void Withdraw(decimal amount)
    {
        // 規則 1：金額必須 > 0
        if (amount <= 0)
            throw new DomainException("金額必須大於 0");

        // 規則 2：帳戶不能凍結
        if (IsFrozen)
            throw new DomainException("帳戶已凍結");

        // 規則 3：餘額必須足夠
        if (Balance < amount)
            throw new DomainException("餘額不足");

        // 規則 4：單日累計上限
        if (DailyTransferred + amount > 1_000_000)
            throw new DomainException("超過單日上限");

        // 通過所有檢查才能改自己的狀態
        Balance -= amount;
        DailyTransferred += amount;
    }

    // ===== 業務方法 2：存款 =====
    public void Deposit(decimal amount)
    {
        if (amount <= 0)
            throw new DomainException("金額必須大於 0");
        Balance += amount;
    }

    // ===== 業務方法 3：轉帳給別人（涉及兩個帳戶） =====
    public void TransferTo(Account other, decimal amount)
    {
        if (other.Id == this.Id)
            throw new DomainException("不能轉給自己");

        this.Withdraw(amount);     // 自己扣（會跑所有規則）
        other.Deposit(amount);     // 對方加
    }
}

Application 層TransferService.cs（DDD 版）

🟧 Service 層變成超薄一層
// ─────────────────────────────────────────────
// 注意：這裡完全沒有業務規則了！
// Service 只做「拿資料 → 呼叫 Domain → 存回去」
// ─────────────────────────────────────────────
public class TransferService
{
    private readonly IAccountRepository _repo;

    public TransferService(IAccountRepository repo) => _repo = repo;

    public void Transfer(int fromId, int toId, decimal amount)
    {
        // 1. 拿資料
        var from = _repo.Get(fromId);
        var to = _repo.Get(toId);

        // 2. 把工作交給 Domain（規則都在 Account 內）
        from.TransferTo(to, amount);

        // 3. 存回去
        _repo.Save(from);
        _repo.Save(to);
    }
}

5.2 同一個 bug 寫不出來

小明還是要做 BonusService。他試圖寫：

小明試圖寫 bug
public void AddBonus(int accountId, decimal bonus)
{
    var account = _repo.Get(accountId);
    account.Balance += bonus;   // ← 編譯錯誤！
    //      ↑ Balance is a 'private set' property
    _repo.Save(account);
}
✅ 編譯就擋下來了

因為 Balance 是 private set;，任何外部程式碼都無法直接賦值。
小明只能用 account.Deposit(bonus)，而 Deposit 內部會檢查 amount <= 0。
規則跟資料綁在一起，無法繞過。

關鍵差異

N-Tier 的規則寫在 「動作（Service）」 上 — 只保護那一個入口。
DDD 的規則寫在 「資料（Account）」 上 — 保護所有入口。
這就是 DDD 比 N-Tier 安全的根本原因。

5.3 測試變超簡單

❌ N-Tier 測試「餘額不足」

[Test]
public void Test()
{
    var mock = new Mock<IAccountRepository>();
    mock.Setup(r => r.Get(1))
        .Returns(new Account {
            Id=1, Balance=50 });
    mock.Setup(r => r.Get(2))
        .Returns(new Account {
            Id=2, Balance=0 });

    var svc = new TransferService(
        mock.Object);

    Assert.Throws<Exception>(() =>
        svc.Transfer(1, 2, 100));
}

15 行，需要 Mock，要建 Service。

✅ DDD 測試「餘額不足」

[Test]
public void Test()
{
    var account = new Account(
        balance: 50);

    Assert.Throws<DomainException>(
        () => account.Withdraw(100));
}

4 行，沒 Mock，沒 Service，沒 DB。
純粹測「規則」本身。

✅ DDD 為什麼好測試

因為業務規則被搬到「沒有外部依賴」的 Account 裡。
Account 不依賴 Repository、不依賴 DB、不依賴任何框架。
所以測試只要 new Account()，呼叫方法、驗結果。完全沒有 Mock 的必要。

把規則塞進 Account 只是 DDD 的第一步。下面這幾節是 DDD 還會教你的重要技巧 — 都很實用，少一個都會在實務踩坑。

5.4 兩個動作要一起成功 — Transaction

仔細看 5.1 的 Transfer：

🟧 TransferService.cs（藏著一個嚴重 bug）
public void Transfer(int fromId, int toId, decimal amount)
{
    var from = _repo.Get(fromId);
    var to = _repo.Get(toId);
    from.TransferTo(to, amount);

    _repo.Save(from);   // ← 假設這行成功，A 的錢扣了
    _repo.Save(to);     // ← 但這行剛好斷電 / 程式爆炸 / 資料庫掛掉？
}
🔴 真實後果

A 帳戶錢扣了，但 B 帳戶錢沒加上去。錢憑空消失。
生產環境這是 P0 級事故（最嚴重的事故等級）— 銀行直接虧錢。

轉帳必須做到：要嘛兩邊都成功，要嘛兩邊都失敗，沒有「只成功一半」這種狀態。這個保證叫做 Transaction。

術語
Transaction 交易（資料庫的）

把多個資料庫操作綁成「一組」。要嘛全部寫入成功（叫 commit，提交），要嘛全部不算數（叫 rollback，回滾，回到動作前的狀態）。資料庫本身就提供這個能力，你只要呼叫它。

修正後的寫法

🟧 TransferService.cs（包進 Transaction）
public void Transfer(int fromId, int toId, decimal amount)
{
    using var tx = _db.BeginTransaction();   // ① 開始一個交易
    try
    {
        var from = _repo.Get(fromId);
        var to = _repo.Get(toId);
        from.TransferTo(to, amount);
        _repo.Save(from);
        _repo.Save(to);
        tx.Commit();   // ② 全部都做完，正式提交（這時資料才真的寫進 DB）
    }
    catch
    {
        tx.Rollback(); // ③ 中間任何錯誤，整個操作回到起點，A 的錢不會被扣
        throw;         //    把錯誤往上拋，讓上層知道這次失敗了
    }
}
用寄錢比喻

沒交易：你掏錢出來、半路被風吹走 — 你也沒了，朋友也沒收到。
有交易：銀行櫃員看到你跟朋友的所有動作完成才蓋章；中途出錯，前面動作全部取消、退錢給你。

5.5 用「型別」幫你擋 bug — Value Object

5.1 的 Withdraw 簽章是 Withdraw(decimal amount)。看起來沒問題，但有個隱藏地雷。

想像你的銀行做國際生意：

隱藏地雷
var ntdAccount = ...;       // 台幣帳戶
var usdAmount = 100m;       // 100 美金（用 decimal 存）

ntdAccount.Withdraw(usdAmount);
// ↑ 編譯通過！但意思變成「從台幣帳戶扣 100 元」
//   程式以為扣 100 美金，實際扣的是 100 元台幣 — 客戶會炸鍋

decimal 就是個數字，沒有單位。100 是台幣還是美金，從程式碼看不出來。這種 bug 跑起來才會發現，發現時可能已經扣錯一堆人錢了。

DDD 的解法：把「金額」做成自己的型別。這種型別叫做 Value Object。

術語
Value Object 值物件

一個只關心「值是什麼」的物件。沒有 ID、不能改值、所有屬性相等就是同一個。
例子：「金額」（100 元台幣）、「日期區間」（2026/1/1 ~ 2026/1/31）、「地址」。
對比 Entity：Entity 有 ID、有生命週期；Value Object 是「描述性的數值」。

🟪 Domain/Money.cs
// record 是 C# 5+ 的關鍵字，自動產生「不可變」「值相等」的物件
public sealed record Money(decimal Amount, string Currency);

// Money(100, "NTD") 跟 Money(100, "NTD") 視為同一個（值相等）
// Money(100, "NTD") 跟 Money(100, "USD") 不同
🟪 Domain/Account.cs（用 Money 取代 decimal）
public class Account
{
    public Money Balance { get; private set; }   // ← 不是 decimal 了
    public bool IsFrozen { get; private set; }

    public void Withdraw(Money amount)
    {
        // 多一道檢查：幣別必須一致
        if (amount.Currency != Balance.Currency)
            throw new DomainException("幣別不對，不能扣款");

        if (amount.Amount <= 0)
            throw new DomainException("金額必須大於 0");
        if (IsFrozen)
            throw new DomainException("帳戶已凍結");
        if (Balance.Amount < amount.Amount)
            throw new DomainException("餘額不足");

        // 重新算 Balance（record 不能改值，所以 new 一個出來）
        Balance = new Money(Balance.Amount - amount.Amount, Balance.Currency);
    }
}
✅ 編譯器幫你擋 bug

之前 ntdAccount.Withdraw(100m) 跟 ntdAccount.Withdraw(usdAmount) 都會編譯成功。
現在強制要傳 Money，幣別寫在型別裡，不對的幣別還沒跑就被擋下來。

用杯子比喻

用 decimal：「給我 100」— 100 什麼？水？酒？汽油？分不出來。
用 Money：「給我 100 杯水」— 一看就知道是什麼。

5.6 誰跟誰是一夥的 — Aggregate

仔細看 5.1 的 account.TransferTo(other, amount)。寫法很簡潔，但藏了一個 DDD 規則問題。

DDD 把「一定要一起被修改」的物件群組起來，這個群組叫 Aggregate。

術語
Aggregate 聚合

一群緊密相關的物件，外界把它當一個整體看待。
例子：一張訂單 + 訂單裡的明細 = 一個 Aggregate。

術語
Aggregate Root 聚合根

Aggregate 對外的唯一入口。外界只能透過 Aggregate Root 操作裡面的東西。
例子：Order（訂單）是 Root，外界要看明細只能透過 order.Items，不能直接 new OrderItem() 自己亂塞。

本章每個 Account 各自是一個 Aggregate Root。

DDD 有條重要規則：一次 Transaction 內，只能修改一個 Aggregate。但 account.TransferTo(other, amount) 同時改了兩個 Account（兩個 Aggregate Root），違反這條規則。

為什麼這條規則重要？

兩個帳戶可能同時被別人修改（多執行緒，就是程式同時做好幾件事）：

  • 程式 1：用戶 A 轉錢給 B，鎖了 A 帳戶，等 B 帳戶釋放
  • 程式 2：用戶 B 轉錢給 A，鎖了 B 帳戶，等 A 帳戶釋放
  • 結果：兩邊互等 → 系統卡死。這叫 Deadlock（死鎖）。

比較安全的寫法：用 Domain Service

把「跨兩個 Aggregate 的邏輯」抽出來放在獨立的 service。

術語
Domain Service 領域服務

當一個業務動作不屬於任何單一 Entity時，獨立做成一個 service，放在 Domain 層。
例子：「轉帳」涉及兩個帳戶 — 放哪一個 Account 都不對 — 抽成 TransferDomainService。

🟪 Domain/TransferDomainService.cs
public class TransferDomainService
{
    public void Transfer(Account from, Account to, Money amount)
    {
        from.Withdraw(amount);   // 改 Aggregate A
        to.Deposit(amount);      // 改 Aggregate B
        // 邏輯不藏在任一 Account 內，而是在「服務」這一層
        // 兩個 Aggregate 都被改，但邏輯位置很明確
    }
}
用寄禮物比喻

account.TransferTo(other)：兩個朋友直接擠在門口遞東西 — 容易撞到、容易吵架（並發問題）。
用 Domain Service：找一個快遞員幫你們交接 — 雙方不用直接接觸，由第三方協調。

💡 為什麼 5.1 還是用簡化版？

因為 account.TransferTo(other) 對學習來說最直觀 — 一行就看懂在幹嘛。實務上，量小、規則少時這樣寫也沒事。
但業務一複雜、流量一上來，要記得這條規則，把跨 Aggregate 的邏輯抽出來。

5.7 大系統怎麼切？— Bounded Context 與通用語言

到目前為止，DDD 都在教你「怎麼寫好一個 Account」。這是 DDD 的一半 — 叫做戰術設計（Tactical Design，怎麼寫程式碼）。

但真實世界的系統不是只有一個 Account。你有訂單、付款、客服、登入、權限、通知……幾十個業務區塊。怎麼切？

這就是 DDD 的另一半 — 戰略設計（Strategic Design，怎麼劃地盤）。

同一個詞，不同地方意思不一樣

想像你做一個銀行系統。「使用者」這個詞：

在哪個情境「使用者」是什麼
登入系統一個帳號（含 email、密碼、登入紀錄）
轉帳系統一個帳戶持有人（含身分證、手機、地址）
客服系統一個被服務的對象（含問題紀錄、滿意度評分）

如果你硬要把這三種「使用者」做成同一個 User class，這個 class 會塞滿亂七八糟的欄位 — 一個跟轉帳完全無關的「滿意度評分」屬性，掛在轉帳要用的 User 物件上。什麼跟什麼？

DDD 的主張：這三種「使用者」是不一樣的東西，應該用不同的 class，住在不同的「世界」裡。每個世界叫做 Bounded Context。

術語
Bounded Context 有界上下文

一個業務區塊有自己的詞彙、規則、模型。同一個詞在不同 Bounded Context 可以是完全不同的東西。

三個世界
Identity 世界（登入區塊）
  └─ User { Email, Password, LastLoginAt }

Banking 世界（轉帳區塊）
  └─ Account { OwnerName, IdNumber, Balance, IsFrozen }

Support 世界（客服區塊）
  └─ Customer { Tickets, SatisfactionScore }

三個世界各做各的。
跨世界要傳資料時，用事件或 API 把對方需要的部分翻譯一下傳過去。

程式碼長得跟業務一樣 — Ubiquitous Language

每個 Bounded Context 裡面，業務人員、設計師、工程師都用同一套詞彙。

術語
Ubiquitous Language 通用語言

所有人 — 業務、PM、設計師、工程師 — 都用同一套詞彙。讓程式碼長得跟業務文件一樣，溝通不會走樣。

業務說程式碼寫不要寫成
核章SealOff()ApproveDocument()（自創詞）
催收Collect()RetrieveDelinquentAccount()（過度翻譯）
對帳Reconcile()CheckBalance()（不準確）

業務說「核章」，工程師心裡 OS「就是 approve 嘛」自己翻譯成 ApproveDocument() — 結果業務看 code 看不懂、工程師看業務文件也看不懂，每次溝通都要再翻譯一次，誤差不斷累積。

用旅遊比喻

沒做 Bounded Context：拿一張世界地圖，到每個國家亂走 — 路名不認識、交通規則不懂、到處迷路。
有做 Bounded Context：每個國家用當地的地圖，符合當地路名跟交通規則 — 在那個國家就熟門熟路。

⚠️ 沒做 Strategic Design 的「DDD」是假 DDD

很多團隊說自己在做 DDD，但其實只是把 N-Tier 的 Service 改名叫 Entity、加幾個業務方法。
沒有 Bounded Context、沒有通用語言，整個系統一個大 Domain 模型 — Aggregate 會無限膨脹、循環依賴、跟 N-Tier 沒兩樣。
Strategic Design 才是 DDD 真正的價值。

第 6 章：你最大的疑問

6.1 「換 DB 真的有差嗎？N-Tier 不是也只改 Repository？」

你問得很好，這是一個常見誤解。先說結論：如果你的 N-Tier 寫得很乾淨，差異不大。但實務上很少這麼乾淨。

真正的差異：「業務邏輯有沒有沾到 DB」

🟧 N-Tier 常見的「不乾淨 Service」
public class TransferService
{
    private readonly DbContext _db;  // ← 注意：直接拿 EF DbContext

    public void Transfer(int fromId, int toId, decimal amount)
    {
        // 用 LINQ to EF 寫查詢
        var from = _db.Accounts
                      .Include(a => a.Transactions)        // ← EF 特有
                      .AsTracking()                         // ← EF 特有
                      .FirstOrDefault(a => a.Id == fromId);

        from.Balance -= amount;
        _db.SaveChanges();   // ← EF 特有
    }
}
🔴 換成 Dapper 會發生什麼？

Include、AsTracking、SaveChanges 全部要拿掉，因為 Dapper 沒這些。
Service 整個要重寫。N-Tier 寫到後期幾乎都會變這樣。

🟪 DDD 的 Domain 完全乾淨
public class Account
{
    public decimal Balance { get; private set; }

    public void Withdraw(decimal amount)
    {
        if (Balance < amount) throw new DomainException("餘額不足");
        Balance -= amount;
    }
    // ↑ 這個檔案裡沒有 EF、沒有 Dapper、沒有 SQL
    // 連「DB」這個概念都不存在
    // 換 DB 這個檔案永遠不用動
}
真正的差異

不是「N-Tier 換 DB 也只改 Repository」對不對的問題，而是業務邏輯有沒有偷偷沾到 DB 的特性。
N-Tier 沒有強制隔離，工程師圖方便就會在 Service 用 EF 的功能，實務上幾乎一定會發生。
DDD 的 Domain 層因為「不允許參考任何 ORM」，從根本上禁止這件事。

6.2 「層之間還是會互相呼叫，那 CA/DDD 跟 N-Tier 差別在哪？」

這是你最重要的疑問。答案是：「呼叫」沒消失，但「呼叫的方向」變了。

N-Tier：直接依賴下層的具體類別

Clean Architecture / DDD：依賴介面，方向反轉

具體例子說清楚

問題N-TierClean Architecture / DDD

＋ 改 TransferService 建構子		 新增 MongoAccountRepository
Service 完全不動
測試要 Mock 什麼？ 整個 SqlAccountRepository，但它不是介面 → 改寫 Mock IAccountRepository 介面，直接行

💡 一句話講清楚差異

N-Tier：層之間直接呼叫具體類別，業務規則寫在動作上。
Clean Architecture：層之間呼叫介面（依賴反轉），業務規則仍在動作上。
DDD：層之間呼叫介面，業務規則搬進資料本身。

三句話帶走

  1. N-Tier：把程式碼分成幾層，方便組織。但業務規則散落在 Service 裡，容易被繞過。
  2. Clean Architecture：把技術細節（Web、DB、框架）跟業務切開。技術可換，業務不動。介面要定義在「需要它的那一層」，這樣依賴方向才真的反過來。
  3. DDD：規則塞進資料自己（Account、Aggregate），讓資料保護自己。也教你把大系統切成一塊塊獨立的世界（Bounded Context），同一個詞在不同世界可以有不同意思。

你會記得的關鍵畫面

記住這個

看 Account 的 Balance 屬性：

  • public decimal Balance { get; set; } → N-Tier / 貧血模型
  • public decimal Balance { get; private set; } + 業務方法 → DDD

就一個 private 的差別，整個架構哲學就不同了。

下一步學什麼

  1. 找一個你熟的業務場景（學校選課、購物車、訂閱訂單），用三種架構各寫一次。
  2. 每寫完一次就試圖「讓另一個工程師繞過規則」，看你的設計擋不擋得住。
  3. 寫單元測試。注意 N-Tier 跟 DDD 的測試行數差距。
  4. 寫完之後，再回去看其他 DDD 教學，那些一開始看不懂的詞會突然全部看得懂。

何時不要用 DDD / Clean Architecture？

DDD 跟 Clean Architecture 不是越多越好。下面這些情況用了反而拖累進度，N-Tier 才是對的選擇。

情境建議
純 CRUD 後台（功能就是「列表 / 新增 / 修改 / 刪除」）N-Tier 就夠，DDD 是殺雞用牛刀
原型、demo、玩具專案用最快寫得出來的方法，CA/DDD 啟動成本太高
專案壽命 < 1 年N-Tier，不必投資長期維護成本
團隊還不熟悉用「物件」思考程式先補基礎，硬上 DDD 會變「假 DDD」
業務規則很簡單、很少變動N-Tier 加 interface 即可
沒有業務專家可以對話通用語言做不出來，DDD 會變「工程師自己想像」
✅ 最後一句話

架構是工具，不是信仰。選能解決你問題的最簡單那把。
N-Tier 寫得乾淨的系統，比 DDD 寫得糟的系統好上一百倍。
